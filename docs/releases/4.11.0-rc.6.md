# v4.11.0-rc.6 — Installation Credential Persistence

## Compatibility

This release candidate updates the independently maintained **Independent MCP Bridge** distribution for Burp Suite
Community and Professional on Java 21. It retains the v4 Streamable HTTP transport, embedded stdio proxy, all three
negotiated MCP protocol revisions, the exact 21-tool Community and 28-tool Professional names, four Community and five
Professional prompts, and all existing resource URIs, templates, stable references, cursors, approval families, and
structured result contracts from `v4.11.0-rc.5`.

RC6 changes only local bearer-credential persistence, related failure handling and lifecycle evidence, plus the release
identity. A valid RC5-era token in the currently loaded project is migrated once to Burp's installation preference store.
Existing native and stdio client configurations therefore continue to work when that legacy value is available. If the
old no-project in-memory value was already lost before RC6 first loads, the extension must generate one new persistent
credential and clients require a one-time update.

## Security and approval changes

- Stores the loopback MCP bearer credential in Montoya `Preferences`, whose API contract survives extension reloads and
  Burp restarts, instead of project-backed `extensionData`, which is memory-only when Burp has no project file.
- Makes the namespaced installation preference authoritative across project changes. A valid currently loaded legacy
  project token is persisted before it is returned, and only then is the obsolete current-project copy removed. Cleanup
  failure cannot replace the committed credential and is reported without credential material.
- Fails closed rather than serving a newly generated ephemeral token when installation preferences cannot be read or
  written. A malformed installation or legacy value is not silently replaced; the operator must use the explicit rotate
  control. An unconfirmed rotation does not claim success, and the UI requires the operator to re-copy or rotate before
  restarting the listener.
- Serializes first-use migration, generation, and explicit rotation within the extension process. A defensive post-write
  read reconciles a committed write and concurrent in-process config access without logging or persisting token values in
  diagnostics, audit records, release evidence, or project data.
- Adds regression coverage for project replacement, reconstructed Burp lifetimes, migration precedence, corruption,
  read/write failure, uncertain committed writes, concurrent first access, rotation persistence, safe cleanup failure,
  and listener startup failure without an ephemeral credential.
- Extends the exact-byte `serverLifecycle` release gate to require private token equality across a real project switch
  and full Burp restart plus explicit-rotation cutover in both Community and Professional. Eight distinct private token
  inputs and two candidate-bound ordered lifecycle reports are structurally checked; cross-edition token reuse is rejected,
  separate installation/data/project roots must be attested, and credential material remains forbidden in permanent
  evidence.
- Preserves loopback-only binding, strict Host/Origin and bearer validation, constant-time credential comparison,
  project binding, cancellation, approval separation, Emergency read-only precedence, and all RC5 supply-chain gates.

## Known limitations

Montoya Preferences do not expose a cross-process compare-and-set primitive. Concurrent first initialization or explicit
rotation by separate Burp processes using the same OS account is not supported; run one active Independent MCP Bridge
installation per preference profile. A running listener intentionally keeps the credential captured at listener startup,
so an explicit rotation still requires a listener restart and client update.

Only the currently loaded legacy project copy can be deleted during migration. Older unopened project files may retain an
obsolete RC5-era token; RC6 never consults those copies after an installation preference exists, and rotating the current
installation credential makes them unusable by that installation. Exact-byte Community and Professional Burp restart and
rotation evidence, reproducible builds, OSV/npm review, SBOM/checksum/provenance validation, protected smoke attestation,
and no-rebuild publication are still required before this candidate may be published.
