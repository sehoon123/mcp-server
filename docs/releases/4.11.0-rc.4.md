# v4.11.0-rc.4 — Fail-Closed Structured Result Consistency

## Compatibility

This release candidate updates the independently maintained **Independent MCP Bridge** distribution for Burp Suite
Community and Professional on Java 21. It retains the v4 Streamable HTTP transport, embedded stdio proxy, all three
negotiated MCP protocol revisions, the exact 21-tool Community and 28-tool Professional names, four Community and five
Professional prompts, and all existing resource URIs and templates. No tool, prompt, resource, template, stable
reference, cursor, or approval family is removed or renamed compared with `v4.11.0-rc.3`.

RC4 intentionally refines retained tool contracts. Stable non-null structured result members are now emitted explicitly
and marked required in output schemas, including empty collections, zero counts, limits, pagination state, and truncation
flags. Project-binding, page-bound, retry, and uncertain-execution descriptions are self-contained. WebSocket and Scanner
detail reads advertise structured `invalid_argument` and `burp_error` outcomes, and correction-required HTTP,
WebSocket, and Scanner failures consistently set MCP `isError=true`. The Community catalog fingerprint is
`15b9b63ea145194e982fdc4f073931cdbf7afdb340e4b7ad5011222b3c04cdbb`; the Professional fingerprint is
`eb0415096841f806d4f93954126dcf46906b42aa75f130bb4075661690d04486`. Clients should reconnect and rediscover
capabilities after upgrading rather than reusing an RC3 schema cache.

## Security and approval changes

- Stops echoing a caller-supplied project ID as an effective binding when Burp project capture fails. A result exposes a
  project binding only after the current project has been safely captured or rechecked.
- Rechecks the current project after approval, including denial, for HTTP history search, attack-surface metadata,
  Scanner-list, and Collaborator-interaction reads. A transition returns `project_mismatch`; denial never authorizes
  source acquisition or Collaborator client access.
- Converts bounded input-validation, cursor, stale-cursor, and Burp accessor failures into structured outcomes with
  consistent MCP error classification. Read-only `burp_error` guidance permits retry only after checking the current
  project and correcting the Burp-side condition; mutation results preserve their existing uncertain-execution rules.
- Keeps `CancellationException` outside broad Burp-error translation so lifecycle and request cancellation continue to
  propagate to the session execution registry and diagnostics counters.
- Scrubs retained Scanner task IDs, modes, targets, timestamps, and counters when a post-start or post-cancellation
  project boundary cannot be safely re-established. Successful Burp deletion and definitive cancellation publication are
  serialized, and the cancellation timestamp is committed atomically. Sequenced status and issue observations prevent an
  older live sample from demoting a newer terminal state, replacing a newer retained issue count or issue payload, or
  republishing stale telemetry, while independent status-read failures remain visible. A result snapshot is version-checked
  and its atomic attachment marker is rechecked after the project-boundary check, so cancellation or detachment completed in
  that interval suppresses the older live counters and issue data before publication. Superseded issue material is reported
  unavailable rather than being mislabeled as truncated by the caller's result limit. Scanner project observations,
  failed-read watermarks, record attachment, and reset tombstones are
  ordered so an older concurrent read or start cannot roll the boundary backward, survive a reset, or detach a current task.
  Successful cleanup releases any reservation added by a racing reset; a definitive terminal observation also releases a
  detached reservation after an earlier cleanup failure, while genuinely unresolved live cleanup remains capacity-reserved.
  A cancellation racing issue materialization emits no stale issue summaries or counts. Issue-read denial remains distinct
  from technical or terminal task unavailability.
- Adds recursive catalog tests requiring every advertised non-null output property to be schema-required and every
  truncation-flagged string companion to advertise its actual `maxLength`, plus wrapper-level tests for structured error
  payloads and `isError` behavior. Empty and budget-limited pages remain complete, bounded, and unambiguous.
- Separates Collaborator `hasMore` from `scanLimitReached`: `hasMore` now reports only known matching omissions inside
  the scanned window, while unscanned interactions explicitly retain unknown match status.
- Adds an immutable-draft vulnerability gate that requires the exact reviewed 204-coordinate Maven set, a fresh
  zero-finding OSV response, current lock-only npm evidence, and the exact authenticated open Dependabot exception. It
  also enforces monotonic BApp `SerialVersion` against same-UUID SemVer ancestors and archives normalized evidence as
  checksummed, attested release assets.
- Preserves granular approvals, Emergency read-only and YOLO precedence, loopback/bearer restrictions, bounded source
  acquisition, project rechecks, stable-reference validation, audit redaction, and the RC3 cancellation barrier.

## Known limitations

This candidate requires a new immutable draft and a complete exact-byte Community and Professional smoke matrix. RC1,
RC2, and RC3 tags, drafts, assets, and evidence are immutable and cannot validate RC4. Under the current objective state,
publication is `WITHHOLD`: no RC4 exact-byte smoke record exists, and the required repository, tag, Actions, and
independent environment-review controls are not all configured.

Montoya 2026.7 still exposes current project identity but no supported same-process project replacement API or project
lifecycle event. The required `dataApprovalAndProjectTransition` scenario therefore remains `BLOCKED` unless a supported,
objectively attested production transition becomes available. Scanner uncertain-execution presentation still has no safe
deterministic production reconciliation trigger, so `scopeScannerUncertainOutcomes` also remains `BLOCKED`. Neither gate
may be weakened, fabricated, or satisfied with duplicate mutation, caller disconnect, guessed UI actions, test hooks, or
prior-candidate evidence.

Cancellation remains cooperative. A synchronous Burp/Montoya call cannot be preempted before it returns, and an external
side effect that already occurred is not rolled back. `burp_error` describes an observed read/accessor failure or a
Scanner project observation discarded because a newer concurrent boundary check superseded it; it does not prove whether
an independently initiated Burp operation ran. Public publication and protected smoke must not run
until all required scenarios are objectively `PASS` against the exact RC4 bytes and the external release controls are
present.
