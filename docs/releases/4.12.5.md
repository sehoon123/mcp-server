# v4.12.5 — Existing-result reliability

Unofficial **Independent MCP Bridge**, maintained by [sehoon123](https://github.com/sehoon123/mcp-server), not published,
endorsed or supported by PortSwigger. This is a candidate source fragment, not evidence of a tag or publication.

## Compatibility

- Version `4.12.5`, BApp SerialVersion 24. Existing `v4.12.4` and all earlier tags/assets remain unchanged.
- Java 21, Kotlin `2.4.20`, Montoya `2026.7`, MCP SDK `0.14.0`, Ktor `3.4.3`, embedded proxy `2.2.1`, dependency locks
  and negotiated protocol revisions are unchanged. The tool catalogs remain 24 Community / 38 Professional.
- Rediscover additive output schemas: execution start/queue return `firstRequestId`, item results return `requestId`,
  and execution status returns required `resultsComplete`. IDs identify inputs within one execution, not stored traffic;
  an allocated ID is not evidence of acceptance/delivery. An uncertain batch reserves all its input IDs and must not be
  retried automatically. Original nullable/empty/duplicate user labels are preserved in MCP results; Burp's native engine
  labels become internal correlation IDs.
- Existing single-send tools add `responseState` (`available`, `no_response`, `preview_failed`, `unavailable`, or null when
  no observation is returned). Prepared `requestBytes` is not a final-wire measurement. Shared routing result schemas
  contain the new nullable fields too, without acquiring response observations or sending traffic.
- Normal disabled-Site-Map-storage guidance moves from `error` to `warning`; actual preview/accessor failures remain in
  `error`. Existing status, execution state and MCP `isError` classifications remain. Consumers that interpret any error
  string as an execution failure must instead inspect the typed result and must not retry on missing responses.

## Security and approval changes

- No new tool, input field, network action, raw-result retention, automatic Site Map insertion, dependency or approval
  bypass. Existing project/ownership fences, authentication, outbound/request approvals, emergency policy, cumulative
  count/byte bounds and uncertain-action retry restrictions remain.
- Execution metadata is read independently so one failing getter cannot erase an otherwise available ID/status. Unknown
  native labels never guess an input. Terminal reconciliation reads at most 64 results and only label/status for
  never-sent cancellation; no terminal exchange content is materialized. Response callbacks still return `Retention.DROP`.
- Completion coverage is conservative under unreadable/unknown/duplicate/conflicting metadata and invalid native counts.
  It is not a vulnerability verdict or proof that all requests succeeded. Final project/ownership checks discard partial
  observations after lifecycle changes; cancellation propagates, including null-response paths.
- Catalog byte ceilings are narrowly updated to 141,000/211,000 for the reviewed output additions (measured
  140,589/210,711). Tool counts and every runtime input/output limit remain unchanged.

## Known limitations

Actual Community/Professional Burp validation, native Request Execution callback/terminal ordering, supported-client
behavior and task-level/model/performance measurements for these bytes are **NOT RUN**. Unit and loopback MCP fixtures
are not a substitute. Independent GPT-6.1 Sol development review is not a native test or release authorization.

Native calls are not forcibly interruptible or heap-bounded by the preview limits. `no_response` does not prove that a
request was never sent; an incomplete execution result does not prove an input was dropped. Callback results precede
reconciled terminal dropped entries, so result order is neither input order nor a complete chronology. Native terminal
getter failure preserves available callback data with incomplete coverage rather than inventing outcomes.

No exact-source pre-tag dependency result or immutable workflow/publication evidence is implied by this fragment. Required
candidate checks must be completed without changing release gates. A downloadable CI bundle is a development test
artifact, not a tagged release or real-Burp evidence.
