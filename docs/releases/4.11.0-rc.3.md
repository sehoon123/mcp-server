# v4.11.0-rc.3 — Deterministic Session Cancellation Evidence

## Compatibility

This release candidate updates the independently maintained **Independent MCP Bridge** distribution for Burp Suite
Community and Professional on Java 21. It retains the v4 Streamable HTTP transport, embedded stdio proxy, all three
negotiated MCP protocol revisions, the exact 21-tool Community and 28-tool Professional catalogs, four Community and
five Professional prompts, and all existing resource URIs and templates. No tool, prompt, resource, template, stable
reference, cursor, approval family, or retained result schema is removed or renamed compared with `v4.11.0-rc.2`.

The `burp://diagnostics` JSON adds the fixed-cardinality integer field `webSocketSearchActive`. It reports only the number
of WebSocket searches currently inside extension-owned processing and is zero when idle. Existing completed and cancelled
outcome fields retain their meanings. MCP clients must tolerate additive object members as required by the protocol and
should reconnect and rediscover capabilities after upgrading.

Authenticated Streamable HTTP session deletion now cooperatively cancels tool and native-resource jobs registered to both
the transport session identity and the SDK execution-session identity before closing the SDK session. Idle/pressure
eviction, project-boundary reset, listener stop, and extension unload use the same lifecycle hook. This does not make a
caller disconnect itself a session deletion and does not change the wire status of retained tools.

## Security and approval changes

- Adds a bounded, value-free in-flight execution registry. Session activation publishes transport and SDK aliases
  atomically with bounded-session admission; termination removes both aliases and cancels registered coroutine jobs.
  Terminal server shutdown cannot be undone by a late activation or recreated permissive registry.
- Keeps job cancellation outside registry locks, reference-counts a shared coroutine job across wrapper leases, and
  rejects registration after session termination. No project, session, request, tool argument, traffic, credential, or
  path value is exported or persisted by this registry.
- Cancels registered work only after the existing bearer, Host/Origin, protocol, project-generation, and session checks
  have admitted the lifecycle request. An unauthenticated `DELETE` cannot reach the cancellation path.
- Adds the secret-free `webSocketSearchActive` processing barrier and cooperative scheduling at the existing 64-record
  cancellation checkpoints in bounded WebSocket scan-window capture and filtering. Source order, scan bounds, cursor
  identity, project rechecks, and first-failure behavior remain unchanged.
- Strengthens the exact live cancellation runner to require target-side processing, an ordered caller-socket-abort plus
  authenticated-session-delete sequence, return to an idle processing/session plateau, and exactly one server-side
  cancelled outcome with no completed outcome. HTTP admission, client abort, timeout, cleanup, or a lost response alone
  cannot pass the gate.
- Preserves granular approvals, Emergency read-only and YOLO precedence, uncertain-execution guidance, audit redaction,
  numeric-loopback restrictions, bounded session/call admission, and exact catalog/evidence validation.

## Known limitations

Cancellation remains cooperative. A synchronous Burp/Montoya call cannot be preempted before it returns, and an external
side effect that already occurred is not rolled back. The live cancellation artifact proves cancellation after the
ordered abort-and-delete sequence and exact outcome delta; it does not attribute the outcome to either action in
isolation and does not prove safe cancellation of mutations.

This candidate still requires a new exact-byte Community and Professional smoke matrix. The immutable
`v4.11.0-rc.2` tag, draft, assets, and `WITHHOLD` evidence remain unchanged and cannot be reused as rc.3 evidence.
Publication remains blocked unless every protected scenario is objectively `PASS` and external release controls are
present.

Montoya 2026.7 still exposes current project identity but no supported same-process project replacement or project
lifecycle event. Exact live project-transition evidence therefore remains blocked unless a supported, objectively
attested UI transition is available. Scanner uncertain-execution presentation also has no safe deterministic production
trigger; it must not be forced through duplicate mutation, caller disconnect, guessed UI actions, or a test hook in the
release artifact. These gates must remain truthful rather than being weakened to obtain a pass.
