# v4.12.0-rc.4 — Defensive Dependency Remediation

This is an **unpublished test candidate** of the unofficial **Independent MCP Bridge**, maintained by
[sehoon123](https://github.com/sehoon123/mcp-server), not published or supported by PortSwigger.
[Support](https://github.com/sehoon123/mcp-server/issues) belongs to this independent repository.

## Compatibility

- Java 21, Montoya `2026.7`, MCP SDK `0.14.0`, Ktor `3.4.3`, and negotiated revisions `2025-03-26`, `2025-06-18`,
  and `2025-11-25` are unchanged. The compiler language and API level remain Kotlin `2.2`. Community/Professional
  retain 24/38 tools. No endpoint, tool, resource, URI template, or prompt is added or removed.
- This candidate carries the RC3-successor `4.12.0-dev.4` passive-inspection surface forward unchanged: the tool-only
  `get_http_message.headerName` single-header read over explicit `request_headers`/`response_headers`, and the
  `part: "response_mime"` native MIME observation (`stated`, `inferred`, nullable `disagrees`, `skipped`) exposed at
  the tool and at `burp://http/{projectId}/{source}/{id}/response_mime`. Default 8 KiB detail reads, the 256 KiB
  explicit cap, complete-value JSON selection, and byte-continuation metadata are all unchanged.
- **No new capabilities.** Kotlin moves from `2.3.21` to the official stable `2.4.20`. This
  updates the Kotlin Gradle build plugins **and the runtime `kotlin-stdlib`** (the shaded extension now ships
  `kotlin-stdlib 2.4.20`), so it is not a build-only bump. The test-only Apache HTTP stack pulled in transitively by
  the `json-schema-validator` remote loader is pinned via test-scope constraints to `httpclient5 5.6.4`,
  `httpcore5 5.4.3`, and `httpcore5-h2 5.4.3`; these are on `testCompileClasspath`/`testRuntimeClasspath` only, not the
  application compile/runtime or shaded extension classpath. The embedded proxy is `2.2.1` at source
  `ae486d65ab3212b1fce216e6fa283930fe0fc10c`, with JAR SHA-256
  `bb509565d8fa986383f028097ceef4bdf2c1c4b7013300aa2b872da2569eddcf`, also shipping Kotlin stdlib `2.4.20`.
- Kotlin `2.4.20` introduced an overload-resolution behavior change: a String-returning lambda passed to the
  `@OverloadResolutionByLambdaReturnType` `mcpTool` helper is no longer disambiguated from the deprecated Unit overload
  by Unit-coercion. Two call sites (one production paginated helper, one test) now return the equivalent
  `List<ContentBlock>` directly, resolving to the list-returning `mcpTool` overload. This is behavior-neutral (the
  String overload wraps identically) and the deprecated-error Unit guardrail is left intact.
- This successor uses `4.12.0-rc.4` and BApp SerialVersion 17. RC1/RC2 tags, signed source, release fragments, and
  uploaded bytes remain unchanged; these are new candidate bytes, not relabeled RC3 or development bytes.

## Security and approval changes

- No new execution, send, scan, request, or network capability is introduced. Existing authentication,
  source/sensitive approvals, project fences, emergency read-only, cancellation, audit privacy, and
  uncertain-execution/no-automatic-retry rules are unchanged.
- The update is a defensive response to fresh OSV pre-tag findings against the previous build/test graph:
  `httpclient5 5.5.1` (GHSA-hjcp-jmpx-g3qm), `httpcore5 5.3.6` (GHSA-hf6x-8p5f-cgmf),
  `httpcore5-h2 5.3.6` (GHSA-v3jc-474w-2wm6), and `kotlin-gradle-plugin 2.3.21` (GHSA-r937-wjx7-w2jp). The updated
  coordinates were resolved from official `repo.maven.apache.org` metadata; the new artifact SHA-256 digests were
  verified against Maven Central and pinned in `gradle/verification-metadata.xml`. No blanket force, global override,
  or verification disable was used, and strict SHA-256 verification remains enabled.
- The runtime license mapping remains strict: the only changed runtime coordinate is `kotlin-stdlib` (Apache-2.0,
  unchanged mapping). The test-only HTTP stack is not part of the runtime SBOM or license bundle.

## Known limitations

- Fresh OSV/npm results must be bound to the exact committed server and embedded-proxy source before tagging.
  A failed or unavailable check blocks tagging. This source fragment alone is not evidence that the gate passed;
  retain its actual outcome with the source, CI, and candidate records.
- Proxy `2.2.1` passed 21 local tests and ordinary CI; the embedded JAR matches the successful CI bytes. These are not
  live Burp results. Its first CI attempt exposed missing cold-cache metadata checksums: the correction preserves the
  previously trusted baseline and reviewed new hashes, rather than disabling verification. One additional metadata
  POM was checked against official Maven Central bytes and its SHA-1 sidecar. No package signature verification claim
  is made. A non-clean diagnostic build changed ZIP entry order; canonical clean builds and CI matched byte-for-byte.
- The formal RC7 observation contract, the historical `security/release-maven-coordinates.txt` baseline, the frozen
  GitHub Actions workflows, and `release/v4.11` are intentionally untouched here. The separate local baseline
  `security/v4.12-candidate-maven-coordinates.txt` contains all **208** updated coordinates, SHA-256
  `59f86f52a3504d5e4314c34e67fa548a6066b1042f4d24a755dcd1a8de190efb`; the frozen formal 204-coordinate contract is not
  this candidate's graph. The current compiler and its Kotlin 2.4.0 ABI-compatibility toolchain are both included. Obsolete bindings for the
  removed `kotlinInternalAbiValidation` configuration were cleaned from both lockfiles after confirming that the
  configuration no longer exists; dependency queries are not filtered to conceal findings.
- The v4.11 predecessor identity bridge, exact-byte Community/Professional smoke, fresh immutable-source vulnerability
  evidence, independent isolated reproducibility, complete legal/source/SBOM/provenance validation, and protected
  publication remain required. Ordinary CI and local matching bytes are not substitutes. The historical vulnerability
  report is not RC4 evidence. The companion proxy's advancing `main` also no longer matches the historical RC7 pin;
  that frozen release line needs a separately reviewed successor, not backdated evidence. A manually staged draft with
  a JAR, SBOM, and checksums is for maintainer testing, not a
  complete attested immutable release, and must remain unpublished. The one-shot formal pipeline cannot retrofit that
  same draft; use a successor candidate after satisfying its gates. Existing immutable tags and assets must never be
  moved or replaced.
- Actual Burp/client testing is still required, including the carried-over header/MIME reads and reconnect/rediscovery
  behavior. Offline tests do not establish issue persistence, native ranking/keyword semantics, or execution cleanup
  behavior. All [RC3 limitations](4.12.0-rc.3.md) still apply.

Before creating the signed annotated RC4 test tag, fresh local OSV/npm checks against its committed source and the
freshly embedded proxy must pass; a failed or unavailable pre-tag check stops tagging and staging. The tag must point
to the reviewed signed source commit and must never be moved. Stage only the JAR and SBOM from successful CI at that
exact SHA, plus checksums computed over those bytes; do not rebuild for upload. Redownload the staged assets and verify
bytes, hashes, manifest identity, and tag/source linkage before handing the draft to the maintainer. This local
preflight and ordinary CI are not the authoritative tagged-workflow vulnerability attestation or formal publication
approval.
